telepatch / design note

Telepatch Execution Model

Roles and tasks are written as plain imperative Rust. Running them does nothing; it records a trace. The engine turns the trace into a per-host graph, merges what can be merged, and streams it into persistent shells over SSH, with a terminal stream per operation.

The split

Batching across roles only works if the playbook describes operations instead of performing them. So the design has two parts that never share an address space: the playbook program and the engine. The target hosts run nothing of ours; they run a shell.

Shells over SSH

An operator doing this by hand keeps a terminal open and runs the steps one after another. Telepatch does the same thing. Each host gets a small number of persistent shells, opened once at the start of a run, and ops are streamed into them for as long as the run lasts. Ansible's per-task cycle of connect, copy a module, run it, collect JSON, disconnect does not exist here. There is no agent, no binary to push, nothing to bootstrap, and nothing for the host to run except the shell it already has.

Opening shells

The transport is the user's own ssh binary, spawned as ssh host bash. Their ~/.ssh/config decides everything about how that connects: keys, agents, ProxyJump, ControlMaster. Telepatch does not own those decisions and does not try to. The executor asks the SSH module for the number of shells it would like on each host; the module tries channels on the first connection, opens further connections when a channel is refused, and reports back what it got.

enum   Principal { Root, User(String) }
struct Shells    { got: Vec<Shell>, want: usize, limit: Option<Limit> }
enum   Limit     { MaxSessions, ConnectRefused, AuthFailed, SudoRefused, Other(String) }

fn open(host: HostId, who: Principal, want: usize) -> Shells;   // want is a hint; got.len() is the answer

want is a hint. The executor gets the whole answer up front and plans with it:

  • got == 0 for Root is a host failure, reported like any other unreachable host.
  • got == 1 always works. One shell, no PTY, ops sequential, hangs handled by timeout inside the shell. Everything is designed to be correct at degree one, so a host that only gives one shell is slower, never broken.
  • got >= 2 lets the executor assign roles: the first shell without a PTY for ops whose output is parsed, the second with a PTY for ops a human might watch, any further ones raising per-host concurrency once within-host parallelism exists.

The optimizer never sees any of this. It emits the per-host graph; the executor schedules it onto however many shells it was given, and the UI shows the limit when a host came up short.

Principals

A Root shell is ssh host bash followed by one sudo -n -H bash (-H: root's own HOME, whatever sudoers keeps of the login user's environment); it stays root for the run. Ops run as root by default, which is what the Ansible repo's ansible_become: true already assumes everywhere. A host where sudo -n is refused is reported in prepare and the run stops before apply.

A User(u) shell is a persistent login shell for that user, opened when the host's graph first needs u and closed when it has no more ops for u. It is opened one of two ways, chosen by the pool: a dedicated channel, ssh host 'sudo -n -iu u bash', while the host has sessions to spare; or by nesting, typing sudo -iu u bash into a root shell, which turns that channel into u's shell until exit. Either way the user has their own login shell and profile, so ~ and ~/.cargo/env resolve the way they would at a terminal, and the user needs no key, password or SSH access of their own. One sudo per user per host per run replaces the repo's getent passwd + $SHELL -lc on every per-user task.

The executor sends each op to its principal's shell in trace order. Shells for different principals pipeline independently; the executor waits across them only at a dependency edge, such as root creating /opt/x and then u writing into it. That is within-host parallelism for the per-user case, which is the only case the corpus has, without a general reordering pass.

Streaming ops into a shell

An op is a command written to the shell's stdin, wrapped so that its result comes back as a trailer the engine can find. The engine does not wait for one op's trailer before writing the next, so a whole window goes down the pipe as fast as the shell will take it. Only an op with a guard waits, and it waits inside the shell, not in the engine.

The trailer is the only protocol. Each OpKind has a shell template and a Result type, and the template is responsible for emitting a trailer that parses into that type:

# emitted by the file op's template; nonce is per run, id is per op
( umask 022; printf %s "$content" | base64 -d > "$tmp" &&
  if [ "$(sha256sum < "$tmp" | cut -d' ' -f1)" = "$(sha256sum < "$dst" | cut -d' ' -f1)" ]; then rm "$tmp"; changed=0; else mv "$tmp" "$dst"; changed=1; fi
); rc=$?
echo "__tp_${nonce} ${id} {\"rc\":${rc},\"changed\":${changed}}"
struct FileResult { rc: i32, changed: bool }          // parser generated from the type
impl Op for File { type Result = FileResult; fn template(&self) -> Script { … } }

A template that forgets a field fails to compile, not fails at three in the morning. The nonce is random per run so output cannot spoof a trailer. Each op runs in a subshell so working directory and environment never leak from one op to the next; the only state that persists on purpose is the small set of variables guards read.

What the shell gives us for free

  • A real terminal per op. On the PTY shell the bytes between two trailers are exactly what a terminal would have shown: colors, progress bars, cursor movement. The stream log stores them with timestamps, and xterm.js or ghostty-wasm replays them with the same code path as live.
  • Facts in bulk. One dpkg-query -W -f='${Package}\t${db:Status-Status}\n' answers every package question; one stat -c with a format string answers every file question. Non-distro sources' probes join the same prepare batch and run in the op's principal. The engine parses; the host just prints.
  • Interactive ops work. Stdin to the PTY shell reaches whatever is in the foreground, so a prompt that genuinely needs a human can get one, through the UI.
  • Non-Linux hosts work to the extent their shell does. There is no binary to build per architecture and nothing that assumes /proc.

Where POSIX shell gets genuinely ugly for an op, the backstop is a helper script or static binary that telepatch owns, pushed lazily the first time that op kind runs on a host and cached by hash. That is a toolbox the shell calls, not a resident process.

Two costs, on the record: a hung op blocks its shell until the timeout wrapper fires or a second shell kills it, and only the PTY shell can forward stdin cleanly. Both are acceptable.

The trace

Every op the program calls appends a node and returns a handle. Nothing executes during tracing. The trace is a flat, ordered log of three node kinds:

enum Node {
    Op {
        kind:   OpKind,            // Pkg, File, Svc, Shell, User, ...
        host:   HostId,
        inputs: Inputs,
        reads:  Set<Key>,          // effect keys this op depends on
        writes: Set<Key>,          // effect keys this op changes
        guard:  Option<Guard>,     // run only if an earlier op's output says so
        post:   fn(&Key) -> Option<Value>,  // what this op guarantees afterwards
    },
    FactRead { host: HostId, key: Key, value: Value, source: Source },
    Barrier,
}

enum Source  { Confirmed, Postcondition(NodeId) }     // speculation would add Journaled
enum Guard   { Changed(NodeId), ExitOk(NodeId), Not(Box<Guard>), Or(Box<Guard>, Box<Guard>), And(Box<Guard>, Box<Guard>) }

Key is a fine-grained effect address: pkg:nginx, file:/etc/nginx/nginx.conf, svc:nginx, user:deploy. Ops whose effects can't be enumerated (shell) declare writes: *, which makes them a barrier for free. The ordering edges between ops are derived from key overlap, so a user who writes pkg(..) then svc(..).restart() never has to state the dependency.

Two distinctions matter later:

  • A postcondition is what an op guarantees once it has run. After pkg(["nginx"]), pkg:nginx is Installed. This is a contract, not a prediction.
  • An output is something you only know after execution: whether the op changed anything, its exit status, its stdout. Outputs are never awaited by the program. They feed guards, which the executor evaluates at run time.

Handles are owned. Every builder on every handle returns the handle, owned (a cheap clone that names the same node), so a chain binds as written: let daemon = h.file("/etc/docker/daemon.json").content(..);, let unit = h.unit("x.service").content(..).mode(0o644);, then h.svc("docker").restart_on(&daemon);. A builder called on a bound handle as a statement edits the same node: let s = h.svc("sshd"); s.reload(); s.when(g);. The methods every op takes (.when, .at_end, .allow, .allow_fail) return the handle's own type, so h.svc(n).restart().when(g) is still a svc handle. Handles and builders added later follow the same rule: the Fetched handle of h.fetch(..) and its builders (.sha256(..), .via_controller()), the pkg builders of the binary_release source and of package removal (.purge()), and every handle after them.

The fact resolver

The planner sees everything up to the next fact read it cannot answer. So the design question is which reads it can answer without a round trip. The two most common reasons a playbook asks about remote state are: it wants to know about something it just did, and it wants to react to whether an op changed anything. Postconditions handle the first; guards handle the second. What remains is reads of pre-existing state the playbook never touches, and those sync.

When the program awaits a fact, the resolver answers from three sources in order.

fn resolve(&self, host: HostId, key: &Key) -> Answer {
    // 1. Already read this run, and no op since has written this key.
    if let Some(v) = self.confirmed.get(&(host, key)) {
        return Answer::Now(v, Source::Confirmed);
    }
    // 2. An earlier op in the pending trace guarantees it.
    if let Some(op) = self.pending.last_writer(host, key) {
        if let Some(v) = (op.post)(key) {
            return Answer::Now(v, Source::Postcondition(op.id));
        }
    }
    // 3. Pre-existing state nobody has touched. Sync.
    Answer::Block
}

Block suspends the program's future. The engine flushes the trace so far (optimize, execute), reads the fact with one round trip, resolves the future, and the program continues. The program is a single async task that is simply paused; there is no re-trace and no requirement that it be deterministic.

Guards, not awaits, for "if changed". changed is an output, so the program cannot await it without blocking. Instead the dependent op is declared with a guard: svc("nginx").restart().when(conf.changed()). The restart is in the graph, the planner sees it, and the executor skips it if the guard is false. Same semantics as an Ansible handler, expressed as a graph edge instead of control flow.

Worked example

Two roles. Three places where the program asks about remote state are marked; only one of them syncs.

#[derive(Template)]
#[template(path = "nginx.conf")]
struct NginxConf { server_name: String, workers: u32 }

#[role]
async fn web(h: &Host<Vars>) -> Result<(), TraceError> {
    // (A) pre-existing state nothing in the playbook writes: this one syncs
    let fresh = !h.exists("/etc/telepatch/.bootstrapped").await;
    if fresh {
        h.user("deploy");
    }
    h.pkg(["nginx", "certbot"]);
    let v = &h.vars.web;
    let conf = h.file("/etc/nginx/nginx.conf").content(NginxConf {
        server_name: v.server_name.clone(),
        workers: v.workers,
    });
    // (B) output of an op: a guard, never awaited
    h.svc("nginx").restart().when(conf.changed());
    h.svc("nginx").enabled();
    Ok(())
}

#[role]
async fn monitoring(h: &Host<Vars>) -> Result<(), TraceError> {
    h.pkg(["prometheus-node-exporter"]);
    h.svc("prometheus-node-exporter").enabled();
    // (C) answered by the postcondition of web's pkg op; no round trip
    if h.pkg_installed("nginx").await.is_some() {
        h.file("/etc/prometheus/targets/nginx.yml").content(NGINX_SCRAPE);
    }
    Ok(())
}

The engine loop

Because the program is a suspended future rather than something to re-run, the loop is short.

async fn run(playbook: impl Playbook, hosts: &[HostId]) -> Report {
    let engine = Engine::new(hosts);
    let mut program = playbook.start(engine.client());   // a future; nothing runs yet

    loop {
        // Drive the program until it finishes or blocks on a fact read.
        match engine.trace_until_block(&mut program).await {
            Traced::Done => {
                engine.flush().await;            // optimize + execute what's pending
                break;
            }
            Traced::Blocked { host, key, waker } => {
                engine.flush().await;            // everything before the read must run first
                let v = engine.read_fact(host, &key).await;   // one round trip
                engine.confirmed.insert((host, key), v.clone());
                waker.resolve(v);                // program resumes on the next iteration
            }
        }
    }
    engine.report()
}

impl Engine {
    async fn flush(&mut self) {
        // Non-mutating nodes (fact reads, secret, fetch, render) always run now.
        // Mutations are deferred until the trace ends or a read needs them;
        // see "Prepare phase" below.
        let pending = self.trace.drain_ready();
        self.prepare(&pending).await?;          // gate: any failure stops the run here
        let graph   = optimize(pending);
        self.executor.run(graph).await;         // per-host queues, cross-host parallel
        // Anything an executed op wrote is no longer confirmed.
        self.confirmed.retain(|(h, k), _| !graph.wrote(*h, k));
    }
}

Guards are evaluated on the host: the template for a guarded op tests a shell variable its source op set, and emits a trailer with skipped: true if the test fails. The stream log sees every node either way, so a skipped restart shows up in the UI as skipped, with the reason, without the engine having made a round trip to decide it.

The optimizer

Three passes over the pending trace, per host. The first version is deliberately conservative about reordering.

fn optimize(trace: Vec<Node>) -> Graph {
    let mut g = Graph::from_trace(&trace);

    // 1. Edges. Trace order is kept within a host. An edge is recorded
    //    where effects overlap, because that is what merging must respect.
    for (a, b) in g.pairs_in_trace_order() {
        if a.host == b.host && (a.writes ∩ b.reads ≠ ∅ || a.writes ∩ b.writes ≠ ∅
                               || a.is_barrier() || b.is_barrier()) {
            g.edge(a, b);
        }
    }

    // 2. Merge. Same host, same mergeable kind, same guard, and nothing
    //    between the earliest and latest member conflicts with the members'
    //    effects. The merged node sits at the earliest member's position.
    for group in g.candidates(|n| n.kind.mergeable()) {
        if g.hoist_is_safe(&group) { g.merge(group); }
    }

    // 3. Schedule. One queue per host in graph order; hosts run in parallel.
    g.schedule_per_host()
}

Pass 2 is what turns five pkg calls across five roles into one apt install. The hoist check is the safety rule: pulling node-exporter's install forward past file nginx.conf is fine because the file op does not read or write any pkg: key. Pulling it past a shell that declares writes: * is not.

Within-host parallelism (running two unrelated ops on the same host concurrently) is a later pass. It is only as safe as the declared effects are honest, so it should wait until there is a body of real roles to check against.

What it costs

Counted from the model for the example above, on a warm run where nothing needs changing. An exchange is one serialized engine-to-host step: a fact read, or executing a window. Seconds depend on your hosts; the counts don't.

The rule of thumb: a run costs about k + 1 windows per host, where k is the number of reads of pre-existing state that nothing in the playbook writes. Everything else the playbook asks is answered from the trace. For a typical playbook k is small, often one or zero, and the hosts run those windows in parallel.

Author-defined resources

When no primitive fits, the author writes a typed resource once. The role then calls it like any other op.

Status: designed

the resource
/// A terminfo entry compiled into the system database.
pub struct Terminfo {
    pub name: String,
    pub source: String,
}

impl Resource for Terminfo {
    const KIND: &'static str = "terminfo";

    fn key(&self) -> Key {
        Key::new(Self::KIND, &self.name)
    }
    fn probe(&self) -> Probe {
        Probe::stdout(cmd!("infocmp -x {}", self.name)).missing_is_none()
    }
    fn plan(&self, now: &Probed) -> Change {
        match now.stdout() {
            Some(text) if text == self.source => Change::None,
            Some(_) => Change::will("replace"),
            None => Change::will("compile"),
        }
    }
    fn apply(&self) -> Script {
        cmd!("tic -x -").stdin(&self.source)
    }
}

});

  • The shell lives inside the resource, once, where it is typed, quoted by cmd! and unit-tested against recorded probes.

  • A restart or reload with no guard is the policy error UnguardedRestart.
  • Permitted with .allow(..), the op runs on every run and the plan says so.
  • When the guard is false the op is skipped, and the run shows it as skipped.
  • A restart of a unit that the same run starts is dropped. The start already runs the new configuration. "Starts" is exact: the unit was not active and the op started it. An op that only enabled or unmasked a unit that was already running does not drop the restart.

Change triggers

An op that depends on a change carries a guard that names the change.

Status: built: .changed() and .ok() on every handle, | & !, evaluation in the shell (a variable for a source earlier in the same run, a constant for one already reported), skipped ops, or-joined merges, the merged-pkg member rule and .at_end()

  • A guarded op whose source failed is skipped, not failed.
  • When pkg ops merge, x.changed() means one of that op's own names was installed.
  • Reboots do not use guards. They use marks and a barrier in the playbook.

A download is a prepare-phase value. A file op places it or unpacks it.

Status: built: h.fetch(url).sha256(sum) (a value, owned and cloneable; a fetch no file op takes is never downloaded), .from(f), .unpack(f) with .strip(n) (f by reference or by value), the checksum-keyed cache, the staging directory, the prepare lines and blockers, Unverified. designed: .via_controller()

h.file("/srv/dataset").unpack(tgz).strip(1);

// a host with no route out: the controller downloads and streams it over

h.file("/opt/blob").from(blob);
  • Prepare phase, on the host: download to a staging directory, verify there, and cache under /var/cache/telepatch/ by checksum.
  • .from(f) places the file. .unpack(f) handles tar (gz, xz, zst, plain; told apart by the file's magic, not the url) and zip, and replaces the directory by renaming: the new tree is built in a sibling directory, then swapped in (the old tree is renamed aside first, so a failed swap puts it back). A marker .telepatch-fetch inside the tree holds the checksum and strip it was unpacked from, so a second run changes nothing.
  • The cache is /var/cache/telepatch/sha256/<sum>, staging is /var/tmp/telepatch/<run>/; a cache entry whose checksum no longer matches is fetched again, and a cache hit makes no network call and needs neither curl nor wget.
  • In prepare, on the host: curl -fsSL, else wget; a failed download, a checksum mismatch, neither tool, an archive of no known format, or a missing unpack tool (unzip or bsdtar, zstd, xz, tar) blocks the host before anything is applied, naming it. Prepare says fetch <url>: cached, fetched, sha256 ok or fetched, not verified.
  • A role may install the downloader in the same window: when a distro pkg op naming curl or wget comes before a fetch or a binary release in a window, the plan prints the window's split candidate after that op, -- split after #12 (pkg curl) when the host has neither curl nor wget: #15 needs a download --. It is decided in prepare. With curl or wget on the host the window runs whole, as without the line. With neither, and only ops after the installing op needing one, nothing of the window is sent: the ops up to and including the installing op run as the window, and the rest is formed again as the next window and prepared afresh, with the tool now there. The run says == host [prepare] window 1: neither curl nor wget is on the host; split after #12 (pkg curl): #15 runs in window 2 == (a window_split event, and a line in the report). No barrier is written by the role. A download needed before the installing op, or with no installing op in the window, blocks as above.
  • A fetch with no checksum is the policy error Unverified, carried by the file op that takes it (.allow(Policy::Unverified, reason) there). An allowed one is staged and never cached, and the executor removes the staging directory when the host is done.
  • Software with a binary and a version is a pkg, not a fetch.

Twelve lines and no shell. Everything is a plain method call, so rust-analyzer completes it, errors point at the right line, and a role can call any crate. Oh My Zsh's installer script is a git clone with extra steps, so the clone is the op. The cost is the h. and s. prefixes and the quoting, which is Rust's, not shell's. ~ expands on the host because the op runs in the user's login shell.

Option B: sh! with interpolation and effects

Same as A, but where no primitive exists yet a shell line goes through a macro that interpolates Rust values with shell quoting and lets checks ride as named arguments. It is the escape hatch, not a style: every sh! in a role body is reported as a warning, and the line above it names the primitive that would replace it (No shell in a role body). The one left in the ported roles:

// HACK(repo: deb-src on the distro's own sources): no primitive edits the distro's .sources files
sh!(h, "sed -i 's/^Types: deb$/Types: deb deb-src/' {sources}",
    unless = "grep -q '^Types: deb deb-src$' {sources}");

{sources} becomes '/etc/apt/sources.list.d/ubuntu.sources' on the wire, so a value with a space or a quote cannot break the command. This is a small macro_rules! plus a quoting function, not a parser. The plan ends with warning: sh! in a role body at src/roles/src_repos.rs:99; a warning never fails the gate.

Option C: a line-oriented DSL in a proc macro

tp! { h,
    pkg zsh
    line /etc/zsh/zprofile "emulate sh -c 'source /etc/profile'"
    for u in admin_users {
        user shell=/usr/bin/zsh

This is the closest to a script, and it is a second language. The proc macro parses token trees, so paths and flags mostly work unquoted, but anything with shell metacharacters needs quoting anyway, loops and conditionals have to be re-invented inside the macro, errors come out as "unexpected token" at the macro boundary, and rust-analyzer sees an opaque block. It compiles down to A, so it can be added later without changing anything underneath.

Option D: real script files

include_tp!("zsh.tp") with the same grammar as C in its own file. Gains shell-style syntax highlighting; otherwise identical cost to C. Mentioned for completeness.

Decision: A, with B as the warned escape hatch. Every op is a builder, because its options are typed and its inverse is known: pkg, file, git, fetch, svc, unit, user. Where none fits, the author writes a typed resource once, and the shell lives inside it. sh! in a role body is a missing primitive: it is reported as a warning and carries a // HACK(<primitive>): what is missing comment. The conventions that make A read well: one op per line, no trailing .await on ops (they return handles, not futures). Builder defaults such that the common case takes no options: pkg([..]) alone means present, file(p).content(c) alone means mode 0644 root. as_user as a scope so become_user is written once per block, not per task. The os fact as an enum so distro dispatch is a match in the role, not seven include files. Reconsider C once there are twenty roles written in A and the h. noise is measurable rather than imagined.

Prepare phase: fail early

The repo fetches binaries, reads OpenBao secrets and prompts for passwords in the middle of plays, with delegate_to: localhost. A missing secret fails after the packages are installed and the user is created. That is the late failure this phase exists to remove.

The rule: anything that can fail without touching a host runs before anything that touches a host, and a failure there ends the run with nothing changed. Concretely the prepare phase does, for every host in parallel:

  • Secrets. Every Secret var reference the trace used is resolved from its backend (bao, env, file, prompt), one read per path. Any miss fails the run and names the var and the role that needed it (Secrets).
  • Downloads. Every fetch(..) runs on its host: download to /var/tmp/telepatch/<run>/, verify the checksum there, reuse the on-host cache when the checksum matches. Network and checksum failures happen here, per host, before anything moves into place. The controller only downloads when a fetch says .via_controller().
  • Templates. Every template value given to file(..).content(..) or unit(..).content(..) is rendered, per host. A missing variable or a wrong type is a compile error, so nothing about a template fails on host forty (Templates).
  • Facts. The bulk fact commands run once per host: os, package state, the getent lines, every exists and stat the trace asked for.
  • Permissions. Did sudo -n -H bash succeed at shell open? Does sudo -iu u true work for every user the roles address? Is curl or wget present on hosts that fetch? These are facts with an assertion attached; the one exception is a downloader an earlier op of the same window installs, where the window splits instead (Fetch and unpack).

Then a gate: if every host passed, apply; if any host failed, report and stop, unless the run was started with a per-host policy that lets the healthy hosts proceed.

How this fits the trace

Nothing in the tracing model changes; the executor's flush gets a rule. When the program blocks on a fact read, the flush used to execute everything pending. Now it executes only non-mutating nodes, which are fact reads and prepare ops (secret resolution, fetch, local_file and local, template rendering), and leaves mutations in the pending list. Mutations run only when:

  1. the trace ends, so the whole playbook's mutations are known and the prepare phase has covered all of them; or
  2. a fact read needs the effect of a pending mutation and no postcondition answers it. That is an implicit barrier: prepare runs for everything before it, apply runs up to it, the fact is read, and tracing resumes.

In the corpus, case 2 is rare. The minio_client role does it (download, then ask the installed binary its hash) and mount_btrfs does it (mkfs, then lsblk). Everything else is case 1, which means for most playbooks the apply phase sees every op on every host before the first one runs. That is also the best possible input to the optimizer: the apt merge now spans the whole playbook, not just the first window.

Secrets never enter the trace as values. A Secret var holds a reference until prepare resolves it; the template that uses it is rendered in prepare with the real value; the rendered bytes go to the host; the stream log records the op as file /etc/telegraf/telegraf.conf (secret) and redacts the content.

Roles as transactions

A role on a host either completes or leaves the host as it found it, to the extent the ops in it allow. That extent is the honest part and it is reported up front.

Mechanism: an undo log

Every tier-one primitive's template captures the state it is about to change and returns it in the trailer. The engine appends an inverse op to a per-role, per-host undo log as each op completes. On failure the log runs in reverse, through the same shell, with the same stream log.

Coverage is a planning output

Because the trace is complete before apply, the engine knows which ops in a role have inverses. The dry run prints it per role: rust_build: 14 ops, 12 reversible, 2 sh without undo. A role is a transaction when every op in it is reversible. A role with irreversible ops still runs, still rolls back the ops it can, and says so; a playbook can be run with --require-transactional to refuse roles that are not.

Scope

Per role, per host. A failure on host X rolls back that role on host X and reports it; other hosts continue, unless the run was started all-or-nothing, in which case every host rolls back that role and the run stops. Roles already completed on X stay; the undo log for a completed role is discarded at commit. Cross-role rollback is not offered: by the time role three fails, roles one and two have been committed on purpose.

The snapshot option

Where the root filesystem is btrfs, zfs or on LVM, a snapshot before a role and a restore on failure is cheaper to implement and more complete than any undo log: it reverts every file, including the ones sh touched without declaring them. It does not revert a running service's state or anything outside the filesystem. It is worth having as an opt-in op, h.snapshot(), that makes the role transactional regardless of its contents on hosts that support it. The repo's own mount_btrfs role suggests the fleet is already partly there.

What this does not promise

  • Anything an installer did on the network (registered a key with a service, posted telemetry) stays done.
  • A sh op without .undo is a hole, and the plan says where the holes are. The alternative, refusing to run roles with holes, is available as a flag and is not the default.
  • Rollback itself can fail. When it does, the host is reported as inconsistent with the exact op that failed, and the undo log is kept on the host for a human.

Semantics to pin down

Effects are the contract

Every op declares reads and writes. Ordering and merge safety are derived from them. shell defaults to writes: *; the user can narrow it with .writes([..]). Lying about effects is the user's problem, the same way changed_when is in Ansible.

Facts vs outputs

A fact is a question about the host (pkg_installed, exists, stat). An output is a result of an op (changed, exit, stdout). Facts are awaited and may block. Outputs are never awaited; they drive guards.

Postconditions are narrow

An op's post answers only keys it fully determines. pkg([x]) determines pkg:x. It says nothing about file:/etc/x/x.conf, even though apt probably wrote it. When in doubt, return None and let the read block.

Controller-side I/O is an op

Reading a controller file or running a controller command inside a role goes through local_file, local_dir or local([argv]), values the engine resolves in prepare without a round trip. It keeps roles replayable, which the dry-run view wants and speculation would need.

Explicit barriers stay

barrier() is an edge from everything before to everything after on that host. It is the escape hatch when effects are too coarse to express an ordering, and it is also what "don't merge these two apt calls" looks like.

Within-host order is trace order

Version one reorders nothing on a host except merge-hoisting. Hosts run fully in parallel. Reordering unrelated ops on one host comes later, once declared effects have earned trust.

Later: speculation

If measured playbooks turn out to sync more than expected, the remaining reads of pre-existing state can be answered from the previous run and verified before anything depends on them. That adds three things and changes nothing else:

  1. Journal. Persist (host, key) → value from each run. The resolver gains a third source, Journaled, consulted after postconditions and before blocking.
  2. Verify. Before executing a window, gather every Journaled read whose key no pending op writes, one batched round trip per host. If a value differs, replace it with the real one and re-trace.
  3. Re-trace. The program becomes something you run from the top again instead of a suspended future, and the prefix that has already executed must come out identical. That is where the determinism rule and local_file become mandatory.

The op model, the optimizer, the executor, the agent protocol and the UI are untouched. The Source enum and the loop grow; nothing else does.

What to prototype first

The part that could turn out to be wrong is small and needs no SSH:

  • A toy op set: pkg, file, svc, sh, with effects, postconditions and inverses.
  • The trace recorder and the resolver, with a fake executor that just records what it would have run, including the deferred-mutation rule.
  • The three optimizer passes, especially hoist_is_safe.
  • A dozen adversarial playbooks: merges that must happen, merges that must not, guards on guards, a sh in the middle of a package run, the same fact read from two roles, a read that forces an implicit barrier.
  • Port zsh and rust_build from the Ansible repo on top of it. They exercise per-user ops and ensure.

Instrument the count of blocking reads per playbook. That number decides whether speculation is ever worth building. The SSH layer, the trailer parser, and the terminal UI are large but they are well-trodden; they are not the part of this design that could be mistaken.
