telepatch / design note

Telepatch Execution Model

Roles and tasks are written as plain imperative Rust. Running them does nothing; it records a trace. The engine turns the trace into a per-host graph, merges what can be merged, and streams it into persistent shells over SSH, with a terminal stream per operation.

The split

Batching across roles only works if the playbook describes operations instead of performing them. So the design has two parts that never share an address space: the playbook program and the engine. The target hosts run nothing of ours; they run a shell.

Shells over SSH

An operator doing this by hand keeps a terminal open and runs the steps one after another. Telepatch does the same thing. Each host gets a small number of persistent shells, opened once at the start of a run, and ops are streamed into them for as long as the run lasts. Ansible's per-task cycle of connect, copy a module, run it, collect JSON, disconnect does not exist here. There is no agent, no binary to push, nothing to bootstrap, and nothing for the host to run except the shell it already has.

Opening shells

The transport is the user's own ssh binary, spawned as ssh host bash. Their ~/.ssh/config decides everything about how that connects: keys, agents, ProxyJump, ControlMaster. Telepatch does not own those decisions and does not try to. The executor asks the SSH module for the number of shells it would like on each host; the module tries channels on the first connection, opens further connections when a channel is refused, and reports back what it got.

enum   Principal { Root, User(String) }
struct Shells    { got: Vec<Shell>, want: usize, limit: Option<Limit> }
enum   Limit     { MaxSessions, ConnectRefused, AuthFailed, SudoRefused, Other(String) }

fn open(host: HostId, who: Principal, want: usize) -> Shells;   // want is a hint; got.len() is the answer

want is a hint. The executor gets the whole answer up front and plans with it:

  • got == 0 for Root is a host failure, reported like any other unreachable host.
  • got == 1 always works. One shell, no PTY, ops sequential, hangs handled by timeout inside the shell. Everything is designed to be correct at degree one, so a host that only gives one shell is slower, never broken.
  • got >= 2 lets the executor assign roles: the first shell without a PTY for ops whose output is parsed, the second with a PTY for ops a human might watch, any further ones raising per-host concurrency once within-host parallelism exists.

The optimizer never sees any of this. It emits the per-host graph; the executor schedules it onto however many shells it was given, and the UI shows the limit when a host came up short.

Principals

A Root shell is ssh host bash followed by one sudo -n bash; it stays root for the run. Ops run as root by default, which is what the Ansible repo's ansible_become: true already assumes everywhere. A host where sudo -n is refused is reported in prepare and the run stops before apply.

A User(u) shell is a persistent login shell for that user, opened when the host's graph first needs u and closed when it has no more ops for u. It is opened one of two ways, chosen by the pool: a dedicated channel, ssh host 'sudo -n -iu u bash', while the host has sessions to spare; or by nesting, typing sudo -iu u bash into a root shell, which turns that channel into u's shell until exit. Either way the user has their own login shell and profile, so ~ and ~/.cargo/env resolve the way they would at a terminal, and the user needs no key, password or SSH access of their own. One sudo per user per host per run replaces the repo's getent passwd + $SHELL -lc on every per-user task.

The executor sends each op to its principal's shell in trace order. Shells for different principals pipeline independently; the executor waits across them only at a dependency edge, such as root creating /opt/x and then u writing into it. That is within-host parallelism for the per-user case, which is the only case the corpus has, without a general reordering pass.

Streaming ops into a shell

An op is a command written to the shell's stdin, wrapped so that its result comes back as a trailer the engine can find. The engine does not wait for one op's trailer before writing the next, so a whole window goes down the pipe as fast as the shell will take it. Only an op with a guard waits, and it waits inside the shell, not in the engine.

The trailer is the only protocol. Each OpKind has a shell template and a Result type, and the template is responsible for emitting a trailer that parses into that type:

# emitted by the file op's template; nonce is per run, id is per op
( umask 022; printf %s "$content" | base64 -d > "$tmp" &&
  if cmp -s "$tmp" "$dst"; then rm "$tmp"; changed=0; else mv "$tmp" "$dst"; changed=1; fi
); rc=$?
echo "__tp_${nonce} ${id} {\"rc\":${rc},\"changed\":${changed}}"
struct FileResult { rc: i32, changed: bool }          // parser generated from the type
impl Op for File { type Result = FileResult; fn template(&self) -> Script { … } }

A template that forgets a field fails to compile, not fails at three in the morning. The nonce is random per run so output cannot spoof a trailer. Each op runs in a subshell so working directory and environment never leak from one op to the next; the only state that persists on purpose is the small set of variables guards read.

What the shell gives us for free

  • A real terminal per op. On the PTY shell the bytes between two trailers are exactly what a terminal would have shown: colors, progress bars, cursor movement. The stream log stores them with timestamps, and xterm.js or ghostty-wasm replays them with the same code path as live.
  • Facts in bulk. One dpkg-query -W -f='${Package}\t${db:Status-Status}\n' answers every package question; one stat -c with a format string answers every file question. Non-distro sources' probes join the same prepare batch and run in the op's principal. The engine parses; the host just prints.
  • Interactive ops work. Stdin to the PTY shell reaches whatever is in the foreground, so a prompt that genuinely needs a human can get one, through the UI.
  • Non-Linux hosts work to the extent their shell does. There is no binary to build per architecture and nothing that assumes /proc.

Where POSIX shell gets genuinely ugly for an op, the backstop is a helper script or static binary that telepatch owns, pushed lazily the first time that op kind runs on a host and cached by hash. That is a toolbox the shell calls, not a resident process.

Two costs, on the record: a hung op blocks its shell until the timeout wrapper fires or a second shell kills it, and only the PTY shell can forward stdin cleanly. Both are acceptable.

The trace

Every op the program calls appends a node and returns a handle. Nothing executes during tracing. The trace is a flat, ordered log of three node kinds:

enum Node {
    Op {
        kind:   OpKind,            // Pkg, File, Svc, Shell, User, ...
        host:   HostId,
        inputs: Inputs,
        reads:  Set<Key>,          // effect keys this op depends on
        writes: Set<Key>,          // effect keys this op changes
        guard:  Option<Guard>,     // run only if an earlier op's output says so
        post:   fn(&Key) -> Option<Value>,  // what this op guarantees afterwards
    },
    FactRead { host: HostId, key: Key, value: Value, source: Source },
    Barrier,
}

enum Source  { Confirmed, Postcondition(NodeId) }     // speculation would add Journaled
enum Guard   { Changed(NodeId), ExitOk(NodeId), Not(Box<Guard>) }

Key is a fine-grained effect address: pkg:nginx, file:/etc/nginx/nginx.conf, svc:nginx, user:deploy. Ops whose effects can't be enumerated (shell) declare writes: *, which makes them a barrier for free. The ordering edges between ops are derived from key overlap, so a user who writes pkg(..) then svc(..).restart() never has to state the dependency.

Two distinctions matter later:

  • A postcondition is what an op guarantees once it has run. After pkg(["nginx"]).installed(), pkg:nginx is Installed. This is a contract, not a prediction.
  • An output is something you only know after execution: whether the op changed anything, its exit status, its stdout. Outputs are never awaited by the program. They feed guards, which the executor evaluates at run time.

The fact resolver

The planner sees everything up to the next fact read it cannot answer. So the design question is which reads it can answer without a round trip. The two most common reasons a playbook asks about remote state are: it wants to know about something it just did, and it wants to react to whether an op changed anything. Postconditions handle the first; guards handle the second. What remains is reads of pre-existing state the playbook never touches, and those sync.

When the program awaits a fact, the resolver answers from three sources in order.

fn resolve(&self, host: HostId, key: &Key) -> Answer {
    // 1. Already read this run, and no op since has written this key.
    if let Some(v) = self.confirmed.get(&(host, key)) {
        return Answer::Now(v, Source::Confirmed);
    }
    // 2. An earlier op in the pending trace guarantees it.
    if let Some(op) = self.pending.last_writer(host, key) {
        if let Some(v) = (op.post)(key) {
            return Answer::Now(v, Source::Postcondition(op.id));
        }
    }
    // 3. Pre-existing state nobody has touched. Sync.
    Answer::Block
}

Block suspends the program's future. The engine flushes the trace so far (optimize, execute), reads the fact with one round trip, resolves the future, and the program continues. The program is a single async task that is simply paused; there is no re-trace and no requirement that it be deterministic.

Guards, not awaits, for "if changed". changed is an output, so the program cannot await it without blocking. Instead the dependent op is declared with a guard: svc("nginx").restart().when(conf.changed()). The restart is in the graph, the planner sees it, and the executor skips it if the guard is false. Same semantics as an Ansible handler, expressed as a graph edge instead of control flow.

Worked example

Two roles. Three places where the program asks about remote state are marked; only one of them syncs.

#[role]
async fn web(h: Host) -> Result<()> {
    // (A) pre-existing state nothing in the playbook writes: this one syncs
    let fresh = !h.fact(Fact::exists("/etc/telepatch/.bootstrapped")).await?;
    if fresh {
        h.shell("useradd -m deploy").writes([Key::user("deploy")]);
    }
    h.pkg(["nginx", "certbot"]).installed();
    let conf = h.file("/etc/nginx/nginx.conf").content(tpl!("nginx.conf", &h.vars));
    // (B) output of an op: a guard, never awaited
    h.svc("nginx").restart().when(conf.changed());
    h.svc("nginx").enabled();
    Ok(())
}

#[role]
async fn monitoring(h: Host) -> Result<()> {
    h.pkg(["prometheus-node-exporter"]).installed();
    h.svc("prometheus-node-exporter").enabled();
    // (C) answered by the postcondition of web's pkg op; no round trip
    if h.fact(Fact::pkg_installed("nginx")).await? == Installed {
        h.file("/etc/prometheus/targets/nginx.yml").content(NGINX_SCRAPE);
    }
    Ok(())
}

The engine loop

Because the program is a suspended future rather than something to re-run, the loop is short.

async fn run(playbook: impl Playbook, hosts: &[HostId]) -> Report {
    let engine = Engine::new(hosts);
    let mut program = playbook.start(engine.client());   // a future; nothing runs yet

    loop {
        // Drive the program until it finishes or blocks on a fact read.
        match engine.trace_until_block(&mut program).await {
            Traced::Done => {
                engine.flush().await;            // optimize + execute what's pending
                break;
            }
            Traced::Blocked { host, key, waker } => {
                engine.flush().await;            // everything before the read must run first
                let v = engine.read_fact(host, &key).await;   // one round trip
                engine.confirmed.insert((host, key), v.clone());
                waker.resolve(v);                // program resumes on the next iteration
            }
        }
    }
    engine.report()
}

impl Engine {
    async fn flush(&mut self) {
        // Non-mutating nodes (fact reads, secret, fetch, render) always run now.
        // Mutations are deferred until the trace ends or a read needs them;
        // see "Prepare phase" below.
        let pending = self.trace.drain_ready();
        self.prepare(&pending).await?;          // gate: any failure stops the run here
        let graph   = optimize(pending);
        self.executor.run(graph).await;         // per-host queues, cross-host parallel
        // Anything an executed op wrote is no longer confirmed.
        self.confirmed.retain(|(h, k), _| !graph.wrote(*h, k));
    }
}

Guards are evaluated on the host: the template for a guarded op tests a shell variable its source op set, and emits a trailer with skipped: true if the test fails. The stream log sees every node either way, so a skipped restart shows up in the UI as skipped, with the reason, without the engine having made a round trip to decide it.

The optimizer

Three passes over the pending trace, per host. The first version is deliberately conservative about reordering.

fn optimize(trace: Vec<Node>) -> Graph {
    let mut g = Graph::from_trace(&trace);

    // 1. Edges. Trace order is kept within a host. An edge is recorded
    //    where effects overlap, because that is what merging must respect.
    for (a, b) in g.pairs_in_trace_order() {
        if a.host == b.host && (a.writes ∩ b.reads ≠ ∅ || a.writes ∩ b.writes ≠ ∅
                               || a.is_barrier() || b.is_barrier()) {
            g.edge(a, b);
        }
    }

    // 2. Merge. Same host, same mergeable kind, same guard, and nothing
    //    between the earliest and latest member conflicts with the members'
    //    effects. The merged node sits at the earliest member's position.
    for group in g.candidates(|n| n.kind.mergeable()) {
        if g.hoist_is_safe(&group) { g.merge(group); }
    }

    // 3. Schedule. One queue per host in graph order; hosts run in parallel.
    g.schedule_per_host()
}

Pass 2 is what turns five pkg calls across five roles into one apt install. The hoist check is the safety rule: pulling node-exporter's install forward past file nginx.conf is fine because the file op does not read or write any pkg: key. Pulling it past a shell that declares writes: * is not.

Within-host parallelism (running two unrelated ops on the same host concurrently) is a later pass. It is only as safe as the declared effects are honest, so it should wait until there is a body of real roles to check against.

What it costs

Counted from the model for the example above, on a warm run where nothing needs changing. An exchange is one serialized engine-to-host step: a fact read, or executing a window. Seconds depend on your hosts; the counts don't.

The rule of thumb: a run costs about k + 1 windows per host, where k is the number of reads of pre-existing state that nothing in the playbook writes. Everything else the playbook asks is answered from the trace. For a typical playbook k is small, often one or zero, and the hosts run those windows in parallel.
